# 离线队列与确认流程（设计，固件 1.0.9 起）

## 现状和问题

- 板子的每条上报都先写进外置 Flash 队列（992 槽），联网时按 1 条/秒发出，服务器每收到一条回一行 `ok`，板子每收到一个 `ok` 就确认队列里最早的一条。
- 问题一：确认只能一条一条来。串口接收曾经丢字节，几百条记录发出去却没有确认，之后每个 `ok` 只能清一条；上报周期 60 秒时，928 条要十几个小时才清完。
- 问题二：重复和丢失无法区分。板子重启后 `g_sent` 从 Flash 恢复，重发会让服务器收到重复记录；确认丢了不会重发，只能靠队列满了丢最旧的。
- 问题三：每个 `ok` 都要唤醒串口处理一次，对以后的低功耗也不友好。

## 目标

1. 一次确认多条：服务器回一个累计确认号，板子一次清掉所有不大于它的记录。
2. 不丢、不重：丢了能重发，重发的记录服务器只存一份。
3. 兼容：旧固件和旧服务器照旧用单条 `ok`，混用不出错。
4. 低功耗友好：不增加定时器和轮询，确认只在收到 `ok` 行时处理一次。
5. 流量不增加：每包只多几个字节。

## 协议

### 记录编号

- 队列里每条记录已经有一个单调递增的存储序号（Flash 记录头里的 `g_seq`）。发送时把它追加到该行的末尾：`...,q=<序号>`，写在行结束符之前。入队时的内容不变，所以已经在队列里的老记录同样可以带上。
- 队列被清空（恢复出厂、远程抹除）后序号会从头开始，所以再带一个队列代号 `qe=<n>`：每次清空队列加 1，持久化在固件里，`why=boot` 行也带上。服务器以 `(箱, qe, q)` 作为唯一键。

### 确认

- 服务器在确认行里加 `a=<n>`，放在 `v=` 之前：`ok p=60 c=0 l=1 a=1234 v=987`。含义：这个队列代号下，序号不大于 n 的记录我都收到了，可以清掉。
- 没有 `a=` 的 `ok` 保持旧含义：确认最早的一条。
- 固件版本低于 1.0.9 的设备，服务器不发 `a=`。

### 服务器怎么算 n

- 每个箱子、每个队列代号记一个“连续收到的最大序号” `ack_q`。
- 收到序号 `q`：
  - `q <= ack_q`：重复，不再存，回 `a=ack_q`。
  - `q == ack_q + 1`：存入，`ack_q = q`；若更大的序号已经先到，则继续往后推。
  - `q > ack_q + 1`：有空洞，先存入，`ack_q` 不动，回 `a=ack_q`。
- 第一次见到某个队列代号时，把 `ack_q` 设为该代号最早一条的序号减 1，不会把更早的当成缺失。

### 重传

- 板子发出记录后，如果 120 秒内队列头没有前进，而且链路在线，就把发送指针退回队列头，从头按 1 条/秒重发。
- 服务器靠唯一键去重，所以重发是安全的。

## 风险和取舍

- 空洞太多时重传会让板子一直重发同一批，流量增加；这里用“120 秒无进展才退回”限制频率。
- 队列代号如果丢失（Flash 损坏），服务器会把新队列当作第一次见到，不会误丢数据，最多多存一次。
- 旧记录升级时没有 `q=`，不影响，只是这部分仍然走一次一条的旧确认。

## 固件 1.0.15：补传标记和本地读取（2026-11-05）

### 现在的补传是怎么走的
1. 每条上报先分一个递增的队列序号 `q`。
2. 有信号且没有积压：只放进内存里的「在途环」（最多 6 条）并立刻发出，**不写闪存**。
3. 下面三种情况，记录按原来的顺序和 `q` 写进 GD25 末尾的离线区：15 秒内没收到服务器的 `a=<n>`、链路掉了、已经有积压。离线区有 992 条，按 60 秒周期大约能存 16 小时。
4. 恢复信号后按批补发：一批最多 8 条、不超过 900 字节，批与批之间隔 1 秒。
5. 服务器回 `a=<n>`，表示 n 及以前的记录都收到了，设备移走这些记录；回 `ok` 但不带 `a=` 的，什么都不确认。
6. 补发后 2 分钟队列头还没前进，就从队列头重发。重复的记录由服务器按 `q` 去重。
7. 离线区写满时，丢掉最老的 16 条（一个扇区）。服务器会看到这段序号缺口，等 30 分钟后放弃等待；之后再到的记录照样入库。

### 要不要给每条缓存加「未同步」标志位
**不用另加。**
- 离线区本身就是「未同步清单」：队列头到队列尾之间的每一条，都是还没被服务器确认的。服务器确认一条，队列头才往前走一条，指针随即写回闪存，断电重启也不会丢。
- 再加一个逐条的标志位，等于同一件事记两遍：每确认一条都要多写一次闪存，两处还可能对不上。

**这次加的是两样更实用的：**
- **补传标记 `bf=1`**：从闪存队列发出的行，在 `q`、`qe` 后面带 `bf=1`，表示这条当时没能实时送到。服务器认出后，在上报记录的摘要里写「补传」。实时发出的行不带这个标记。
- **本地能直接看还有哪些没同步**：USB 串口发 `queue` 看条数，发 `dump` 逐条列出（见下一节）。

### USB 串口本地读取（USART1 → CH340，9600 8N1）
- 插着 USB（充电器有电）时单片机不进 Stop，命令随时能收；用电池时 CH340 不通电，这个口不用，不影响低功耗。
- **注意**：这一条按「CH340 和充电走同一个 USB 口」来设计。如果不是同一个口，读取时要同时插上充电。
- 每发一行命令，板子回一行或多行，回复都以 `#` 开头，字段之间用空格分隔，每个字段写成 `key=value`。
- 上报行照旧原样镜像到这个口，不带 `#`，程序按开头的字符就能区分。

| 命令 | 回复 |
|---|---|
| `help` | `#help info queue dump last` |
| `info` | `#info fw=1.0.15 seq= opens= lid= chg= bat= link= t= period= pending= free=` |
| `queue` | `#queue pending= flash= ring= next= qe=` |
| `dump` | 每条一行 `#rec i= q= bf= <原文>`，最后一行 `#end n=<条数>`；最老的在前，`bf=1` 表示已经落盘 |
| `last` | `#last <最近一条上报>` |
| 其他 | `#err cmd=<命令>` |
